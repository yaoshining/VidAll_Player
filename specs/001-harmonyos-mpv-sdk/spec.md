# 功能规格：VidAll_Player HarmonyOS/OpenHarmony TV libmpv 组件库

**功能分支**：`001-harmonyos-mpv-sdk`
**创建日期**：2026-07-21
**状态**：草案
**输入**：建设可发布、可复现、可审计、可在 HarmonyOS/OpenHarmony ARM64 电视真机运行的 VidAll_Player 原生 `libmpv` 播放器组件库；它供既有 VidAll_TV 集成，不改造 VidAll_TV，并提供受控发布、兼容验证与最小集成示例。

## 背景与范围

本功能交付 VidAll_Player：供既有 VidAll_TV 使用的独立原生播放器组件库，而非改造、迁移或发布 VidAll_TV。本库必须作为可安装、可版本化的 ArkTS/ohpm 组件交付，内部受控集成 NAPI、XComponent、EGL/GLES 与 `libmpv`；对外仅暴露稳定、受限且可追踪的播放契约。兼容基线是 VidAll_TV 当前 IJKPlayer 的媒体浏览、WebDAV、SMB localhost HTTP 代理、字幕、音轨、音频路由、硬解回退、播放控制与生命周期场景。适配由 VidAll_TV 集成方在其仓库完成，本库不得修改 VidAll_TV 的源代码、配置、发布物或运行行为。

**本 Issue 的 SMB 边界**：本 Issue 仅冻结并验证既有的 `localhostProxy`/lease 兼容路径，不把它表述为 mpv 原生 SMB 支持。直接播放 `smb://` 需要将 `libsmbclient` 纳入受控 FFmpeg/libmpv 构建、完成许可证/ELF 审计与 ARM64 TV 真机验证；该工作必须在本 Issue 完成后以独立 Issue 跟踪。在此之前，任何文档或能力清单不得将当前 `libmpv.so` 表述为支持 `smb://`。

首期目标设备为 ARM64 电视真机。组件安装兼容下限为 HarmonyOS 5.0.3 / API 15，目标与完整认证基线为 HarmonyOS 6.0.2 / API 22；新增或敏感平台能力须检查 API 19，并为 API 15–18 提供可记录的降级。x86_64 模拟器和 Vulkan 不属于首期支持承诺。

## 用户场景与测试

### 用户故事 1：在电视上稳定播放已选媒体（优先级：P1）

作为 VidAll_TV 用户，我可以在电视上从本地文件或已授权的网络地址开始播放视频，使用遥控器暂停、恢复、跳转、调速、调整音量和结束播放，并在异常时得到可理解的恢复入口。

**优先级原因**：这是替换现有 IJKPlayer 的最小业务价值；无此能力其余网络、字幕和供应链功能均不可独立交付。

**独立测试**：在 ARM64 目标电视上，对本地 MP4 和普通 HTTP 视频完成创建播放器、附着画面、加载、首帧、播放、跳转、暂停、恢复和释放，且重复释放不崩溃。

**验收场景**：

1. **给定** 已创建播放器且已提供有效播放画面，**当** 用户加载可读本地 MP4，**那么** 播放器进入准备、播放状态并显示画面和播放进度。
2. **给定** 正在播放的媒体，**当** 用户连续执行暂停、恢复、相对跳转、百分比跳转、速度、音量和静音操作，**那么** 状态与实际播放一致且不产生额外播放器实例。
3. **给定** 无效 URL、不可读文件或已失效网络连接，**当** 用户尝试播放，**那么** 操作安全失败、显示结构化错误和重试入口，且应用仍可播放下一条媒体。
4. **给定** 播放画面先被销毁或播放器已释放，**当** 业务重复执行销毁、停止或释放，**那么** 调用幂等、无崩溃、无死锁、无悬垂回调。

---

### 用户故事 2：通过 WebDAV 选择并播放私有媒体（优先级：P1）

作为手机或电视用户，我可以输入并保存经授权的 WebDAV 服务配置，浏览目录、选择视频并播放；服务端重定向、分段读取和断网恢复不会导致凭据泄露。

**优先级原因**：WebDAV 是本项目明确的核心媒体来源，也是 VidAll_TV 现有网络媒体场景的关键替代能力。

**独立测试**：使用受控测试 WebDAV 服务，验证目录选择、本地保存的授权配置、Basic Authorization、HTTPS 证书链、重定向、Range 跳转和连接失败后的可恢复错误。

**验收场景**：

1. **给定** 用户已输入有效 WebDAV 地址和凭据，**当** 用户打开目录并选择可播放文件，**那么** 文件列表可导航、所选视频开始播放，且界面与日志均不显示密码或授权头。
2. **给定** WebDAV 服务返回 301、302、307 或 308，**当** 播放器跟随重定向并进行 Range 跳转，**那么** 授权信息在允许的同一受信任服务范围内保持有效，且跳转成功或报告明确失败原因。
3. **给定** 无效凭据、证书不可信、网络断开或服务端超时，**当** 用户加载媒体，**那么** 应用显示可区分的错误与重试入口，不保存明文凭据到日志或发布物。

### 用户故事 3：选择音轨和字幕（优先级：P1）

作为观看多语言媒体的用户，我可以查看音频和字幕轨的语言、标题与类型，切换音轨或字幕，添加外部字幕，并在中文、双向文字和字体缺失时获得可预测的显示或降级结果。

**优先级原因**：多音轨、内嵌/外挂字幕是 VidAll_TV 当前 IJKPlayer 使用场景，且直接影响影视内容可用性。

**独立测试**：对含多音轨与内嵌字幕的视频、网络字幕 URL、SRT 和 ASS 文件执行轨道枚举、连续切换、跳转后稳定性、字幕延迟和错误编码降级验证。

**验收场景**：

1. **给定** 含多个音频和字幕轨的视频，**当** 用户打开轨道选择界面，**那么** 每条轨道显示可用的语言、标题和类型，当前选择清晰可见。
2. **给定** 正在播放的多音轨视频，**当** 用户连续切换音轨并在其间跳转，**那么** 选定音轨保持一致、音画同步正常，失败时给出结构化错误。
3. **给定** 用户添加可访问的外挂 SRT 或 ASS 字幕，**当** 字幕加载完成，**那么** 用户可以启用、关闭和调整延迟；同一内容不会被原生字幕和 ArkTS 覆盖层重复渲染。
4. **给定** 字体缺失、中文/双向文字或异常字幕编码，**当** 字幕显示，**那么** 结果被记录为正确渲染、可识别但降级、或不支持，用户不会遇到崩溃或无提示静默失败。

---

### 用户故事 4：播放流媒体和 SMB 代理媒体（优先级：P2）

作为拥有家庭媒体库的用户，我可以播放 HTTPS 直链、HLS、DASH，或由业务应用转成 localhost HTTP 的 SMB 媒体，并在可跳转、认证和连接恢复上获得与既有播放器一致的行为。

**优先级原因**：这是覆盖 VidAll_TV 网络来源和 IJKPlayer 路由行为的关键扩展，但依赖基础播放和授权能力先可用。

**独立测试**：分别使用 HTTPS、HLS 主/媒体播放列表、DASH 清单以及 SMB localhost HTTP 代理样本，验证加载、分段、跳转、授权、网络中断和代理清理。

**验收场景**：

1. **给定** 有效 HTTPS、HLS 或 DASH 地址，**当** 用户开始播放并执行跳转，**那么** 播放开始或给出协议、证书、网络或格式的明确错误结论。
2. **给定** SMB 媒体已由业务层暴露为 localhost HTTP 地址，**当** 用户播放并跳转，**那么** Range、认证、错误恢复和代理释放行为通过验收记录。
3. **给定** 网络在播放中断开后恢复，**当** 用户选择重试，**那么** 播放器不会泄漏旧连接或旧媒体状态，并恢复播放或显示不可恢复原因。

### 用户故事 5：安装并发布可信组件（优先级：P2）

作为 VidAll_TV 的集成者，我可以从受控私有制品源安装一个版本化的 VidAll_Player ArkTS/ohpm 组件，并仅按公开组件契约接入；作为发布负责人，我可以向 GitHub Release 和批准的私有制品源发布同一经过审计的版本，获得可重建来源、组件包、公开接口说明、依赖与许可证清单、校验值、能力清单和真机证据，并明确区分“已通过真机样本”“已构建待验证”和“不支持或暂缓”。

**优先级原因**：播放器库必须可被业务应用安全地消费和回退；供应链、许可证、版本一致性与设备差异没有可审计证据时，不能作为生产组件发布。

**独立测试**：在 macOS 和 Linux 的干净环境重新执行受控构建；从批准的私有制品源安装指定组件版本到隔离的消费方样例，校验下载内容、组件元数据、产物哈希、ABI、导出符号和系统依赖，并比较发布元数据。

**验收场景**：

1. **给定** 指定组件版本和锁定的上游来源，**当** 在支持的 macOS 或 Linux 环境执行干净构建，**那么** 生成可安装的 ArkTS/ohpm 组件、ARM64 原生产物、公开接口说明、版本信息、校验文件、许可证/NOTICE、SBOM 和机器可读能力清单。
2. **给定** 已批准发布的组件版本，**当** 发布负责人创建 GitHub Release 并发布到私有制品源，**那么** 两个发布渠道引用相同版本、相同来源标识、相同校验值和相同发布说明；任一渠道失败时版本不得标记为已发布。
3. **给定** 隔离的消费方样例，**当** 从私有制品源安装已发布组件并按公开契约创建、控制和释放播放器，**那么** 能完成最小播放冒烟流程，且不需要访问内部原生实现或修改 VidAll_TV。
4. **给定** 任一发布产物，**当** 执行校验与 ABI 审计，**那么** SHA-256、目标 ABI、导出符号及允许的动态依赖均符合发布记录。
5. **给定** 一项容器、编解码器、协议、字幕、硬解、HDR 或音频能力，**当** 发布负责人查看支持矩阵，**那么** 可看到测试样本、目标设备、结论状态和已知限制，而非仅看到构建选项。

### 用户故事 6：在手机或电视示例中验证生命周期（优先级：P3）

作为集成开发者，我可以运行最小示例，在手机或电视上通过焦点可达的界面配置 WebDAV、选择视频、重建播放画面、切换媒体、处理后台恢复和网络异常，并观察资源安全释放。

**优先级原因**：示例降低集成风险，但其价值建立在 SDK 与核心播放流程之上。

**独立测试**：在至少一个目标电视和一个可安装的手机设备上执行遥控器/触控可达性、画面重建、连续切源、后台恢复、网络断开与重复释放手工验收。

**验收场景**：

1. **给定** 示例首次进入，**当** 用户使用遥控器方向键、确认键和返回键操作，**那么** 配置、列表、播放和错误界面始终存在可见焦点且无焦点陷阱。
2. **给定** 正在播放的媒体，**当** 画面重建、应用切换后台再恢复或连续切换多个来源，**那么** 旧资源被释放，新画面可恢复或显示明确恢复失败原因。

### 边界情况

- 播放器在尚未附着画面、画面尺寸为零、画面已销毁或已释放后接收控制调用时，必须安全拒绝或按幂等规则处理。
- 同一媒体在短时间内被多次加载、停止、释放或切换时，必须保持一个可解释状态，不得音频重叠、崩溃或泄漏。
- WebDAV 认证失败、跨域/跨主机重定向、连接复用、Range 失败、无效证书、DNS 失败和 chunked 响应必须有明确且脱敏的错误结论。
- 文件不存在、权限拒绝、路径失效、外部字幕或音频 URL 不可访问、字幕编码异常、字体缺失和轨道在跳转后消失必须可恢复或可解释。
- 对 4K、10-bit、60fps、HDR、杜比视界和高规格音频，未完成目标电视端到端验证前不得标记为已支持。

## 需求

### 功能需求

- **FR-001**：SDK 必须面向 ARM64 HarmonyOS/OpenHarmony 设备提供独立播放器句柄；每个句柄可独立创建、加载、顺序切源、停止和释放，且不得依赖全局播放器或全局图形上下文。
- **FR-002**：SDK 必须支持在可用播放画面附着、尺寸调整、分离和销毁的生命周期内安全处理播放器调用；画面附着时序必须可验证。
- **FR-003**：SDK 必须作为版本化 ArkTS/ohpm 组件提供稳定且受限的公开调用面，至少包含创建、附着/调整/分离画面、加载、播放、暂停、跳转、设置速度、设置轨道、添加字幕、订阅事件和释放；消费方不得依赖内部 NAPI、XComponent、EGL/GLES 或 `libmpv` 实现细节。
- **FR-004**：每个公开调用必须定义线程模型、前置条件、失败条件、幂等性和释放后的行为；外部调用不得绕过受控网络、文件访问和安全策略。
- **FR-005**：播放器必须使用 `idle`、`preparing`、`playing`、`paused`、`buffering`、`completed`、`error`、`released` 等明确状态，并向 ArkTS 提供统一、顺序可追踪的状态更新。
- **FR-006**：SDK 必须支持加载本地文件、HTTP/HTTPS 直链、HLS 和 DASH；RTSP、UDP、SRT、RTMP 仅可在完成单独真机验证后列为可选支持。
- **FR-007**：SDK 必须支持业务层将 SMB 媒体转为 localhost HTTP 地址的策略，并定义 Range、认证、跳转、错误恢复和代理清理验收。
- **FR-008**：SDK 必须支持通过受控请求头完成 WebDAV Basic Authorization；不得使用 URL 用户信息传递凭据，且不得记录、展示或发布账号、密码和 Authorization 值。
- **FR-009**：SDK 必须验证 HTTPS 证书链、SNI、TLS 版本、重定向、Range、chunked 响应、超时、DNS/网络异常和重试行为；跨重定向的授权策略必须遵守受信任范围。
- **FR-010**：SDK 必须支持 MP4/MOV、MKV/WebM、TS/M2TS、AVI、FLV 和 MPEG-PS，并为每类容器记录实际使用的分流器及验证状态。
- **FR-011**：SDK 必须验证 H.264/AVC、HEVC/H.265 Main/Main10、VP9 和 AV1 软件解码；附加视频格式只能在独立验证后声明。
- **FR-012**：SDK 必须分别验证软件解码与 OpenHarmony 硬件解码，并在运行时输出脱敏的硬解状态、实际选定解码器和软硬回退原因。
- **FR-013**：SDK 必须对 1080p、4K、10-bit 和 60fps 在目标电视记录首帧、跳转、缓冲恢复、CPU、内存和长播稳定性边界；未实测不得声称支持。
- **FR-014**：SDK 必须支持 AAC/AAC-LC、MP3、FLAC、ALAC、Vorbis/Opus 和 PCM 的播放验证，并记录样本结论。
- **FR-015**：SDK 必须对 AC-3、E-AC-3、DTS、DTS-HD、TrueHD、MLP 和 Audio Vivid 分别记录可解码播放、仅转码、静音、失败与是否可直通的真机结论。
- **FR-016**：SDK 必须提供多音轨枚举、语言/标题读取、运行时切换、音量、静音和音画同步控制，并验证连续切换及跳转后的稳定性。
- **FR-017**：SDK 必须支持内嵌和外挂 SRT、ASS/SSA、WebVTT、PGS、VobSub 的轨道识别与渲染验证，并将“可识别”与“正确渲染”分别记录。
- **FR-018**：SDK 必须提供字幕轨道枚举、选择、外部字幕添加、延迟调整及样式控制；必须验证中文、双向文字、字体缺失和异常编码的降级行为。
- **FR-019**：SDK 必须提供可审计的 CJK 字体发现和兜底策略，并在首期只启用一种内嵌字幕渲染路径，禁止与 ArkTS 字幕覆盖层重复渲染。
- **FR-020**：SDK 必须支持受控外挂音频和字幕 URL；首期不承诺下载缓存。网络不可访问、下载失败和缓存请求必须给出结构化错误，其中未实现缓存必须稳定报告 `FEATURE_UNSUPPORTED`，不得静默回退或在文档中宣称支持。
- **FR-021**：SDK 必须从真实视频参数事件报告比例、旋转和像素宽高比。首期不提供裁剪、去隔行和截图的公开控制 API；请求或示例入口必须稳定报告 `FEATURE_UNSUPPORTED`，发布说明不得将其列为已支持，直至补充独立 API、测试和 ARM64 TV 证据。
- **FR-022**：SDK 必须确保 SDR 基线正确；HDR10、HLG、杜比视界只能在目标电视完成端到端色彩、元数据和色调映射验证后标记支持。
- **FR-023**：SDK 必须提供加载完成、播放结束、关闭、日志、播放位置、时长、百分比、缓存暂停、缓存状态、轨道列表、视频参数和音频参数等事件。
- **FR-024**：SDK 必须把原生和媒体错误转换为 ArkTS 可消费的结构化错误，至少包括错误域、稳定代码、可读信息、可否重试和脱敏上下文。
- **FR-025**：SDK 必须以线程安全方式将原生事件转发到 ArkTS，并保证回调、画面创建/尺寸变化/销毁、前后台切换和异常释放无泄漏、无死锁、无使用已释放对象。
- **FR-026**：SDK 必须禁止在 UI 主线程执行长时间媒体解析、阻塞网络或阻塞式原生操作。
- **FR-027**：SDK 必须锁定所有上游及传递依赖到不可变版本标识，并记录来源、校验值、许可证和构建配置；不得以浮动分支作为发布输入。
- **FR-028**：SDK 必须能在 macOS 和 Linux 的干净环境通过受控脚本重建；第三方预编译发布物仅可作对照或引导，不能成为生产唯一来源。
- **FR-029**：每次构建必须生成机器可读能力清单，包含构建配置、可用容器/协议/解码器/编码器/滤镜、动态依赖、ABI、最低兼容级别、构建时间和源提交标识。
- **FR-030**：每次发布必须生成 SPDX 或 CycloneDX SBOM、第三方 LICENSE/NOTICE、许可证结论、组件包与公开接口说明、版本元数据、产物 SHA-256、变更日志和已知限制。
- **FR-031**：发布验证必须检查下载校验、可重建性、组件安装、导出符号、ELF ABI、动态依赖白名单以及发布物与版本标签的一致性。
- **FR-032**：SDK 必须维护 VidAll_TV IJKPlayer 行为到 SDK 能力的可追踪矩阵，至少涵盖媒体浏览输入、数据源请求头、WebDAV、SMB localhost HTTP 代理、轨道/字幕回退、音频路由、硬解回退、跳转、播放控制和生命周期；该矩阵仅定义兼容目标，不得要求修改 VidAll_TV。
- **FR-033**：SDK 必须提供最小 HarmonyOS 手机/电视示例。示例（而非公开 SDK）负责经用户授权配置 WebDAV、浏览并选择视频；SDK 仅接收已授权的 `MediaSource`、受控请求头和播放命令。示例必须播放并展示错误，电视界面必须满足遥控器焦点和返回键要求。
- **FR-034**：示例必须覆盖画面重建、连续切源、后台恢复、网络断开恢复和资源释放，并提供可执行的手工验收步骤。
- **FR-035**：SDK 与示例必须以 API 15 为安装兼容下限、API 22 为目标/编译基线；新增或敏感 API 必须核验 API 19 可用性，并记录 API 15–18 降级。
- **FR-036**：项目的需求、设计、计划、任务、测试、验收、发布、变更、风险、代码审查和运维文档必须使用中文；法律、协议、上游原文和代码标识符可保留原文并附中文说明。
- **FR-037**：所有能力结论必须使用“已通过真机样本”“已构建待验证”或“不支持或暂缓”三态，README、组件文档、示例、私有制品元数据和发布说明禁止将已构建表述为已支持。
- **FR-038**：组件发布流程必须在发布前阻断未锁定依赖、缺少 SBOM 或许可证结论、校验失败、能力矩阵缺失、敏感信息泄露、API 15/19/22 兼容记录缺失或 GitHub Release 与私有制品版本不一致的版本。
- **FR-039**：GitHub Release 必须发布供审计与集成使用的版本标签、发布说明、校验与相关发布附件；私有制品发布必须使用批准的访问控制、不可变版本和最小权限凭据，且不得把凭据写入源码、日志、组件包、SBOM 或发布附件。
- **FR-040**：本库必须提供与 VidAll_TV 隔离的消费方集成验证；验证只能使用契约适配或独立样例，不得修改、构建、提交或发布 VidAll_TV。
- **FR-041**：`createPlayer()` 返回的播放器必须由 HAR 内部 ArkTS-NAPI bridge 驱动真实 libmpv 内核；不得以 ArkTS 内存状态机、命令 Promise 或示例页面轮询伪造播放、轨道、缓冲、状态或首帧。
- **FR-042**：`attachSurface`、`resizeSurface`、`detachSurface`、加载、播放控制、轨道/字幕、停止和释放必须逐项映射至内部原生命令；公开 HAR 是唯一消费者边界，候选制品必须交付其所需 native 实现，消费者不得直接依赖 `entry` 私有 `.so` 或调用私有 NAPI。
- **FR-043**：事件必须来自真实 libmpv、渲染器或桥接生命周期，包含可判别 payload、单会话顺序、当前 surface generation 与释放屏障语义。首帧只可在当前 surface 的真实渲染提交后确认；release Promise 完成后不得再回调。
- **FR-044**：SDK 必须独占每个会话的 XComponent Surface、NativeWindow、渲染线程与原生资源所有权；创建、尺寸变化、销毁、重复附着和 surface 重建不得产生跨会话共享、旧 generation 渲染、资源泄漏或悬垂回调。
- **FR-045**：首轮 HTTP/WebDAV 与 SMB localhost HTTP proxy 必须以真实端到端验证为准。重定向认证范围、代理 lease 的取得、续期、释放请求/确认、超时和异常回收必须是可消费的公开契约；业务层只提供已启动的代理 URL 和 lease 标识，不实现解码、渲染、协议恢复或播放器内核。
- **FR-046**：候选发布前，HAR 内部 native packaging、候选 HAR/NAPI ABI 关系、独立 consumer-smoke、ARM64 TV API 22 真机的创建、附着、加载、真实首帧、控制、surface 重建、释放、HTTP/WebDAV 和 SMB proxy 证据必须齐全。API 19 TV 模拟器只能用作兼容辅助，不能替代 ARM64 真机证据。

### 关键实体

- **播放器会话**：一个独立媒体播放实例；包含唯一状态、所附着画面、当前媒体、轨道选择、事件订阅和释放状态。
- **媒体来源**：待播放资源及其来源类型、本地/网络位置、受控请求头、外部音频/字幕、SMB 代理关联和输入校验结果。
- **播放轨道**：音频、视频或字幕轨；包含类型、语言、标题、可选中状态、可识别/可渲染结论和运行时选择状态。
- **播放事件**：播放器产生的状态、进度、缓存、媒体参数、轨道变化、日志或错误通知；包含会话关联、时间、脱敏上下文和顺序信息。
- **能力证据**：某项功能在特定 SDK 版本、构建输入、设备和测试素材上的三态结论、指标、日志摘要和已知限制。
- **受控构建记录**：上游锁定、工具链标识、构建输入、产物、校验、依赖、许可证与 SBOM 的可审计关联。
- **WebDAV 服务配置**：用户授权的服务端地址、显示名称、认证状态和安全保存引用；不得向日志、错误或发布物暴露凭据。

## 假设与依赖

- VidAll_TV 现有 `IPlayer`、IJKPlayer 适配器、媒体浏览、WebDAV、SMB localhost HTTP 代理、字幕桥、音频路由、硬解回退、播放控制和生命周期是兼容性的事实基线；其当前行为需在实现前转为可追踪矩阵。本库只消费经授权的基线证据，不修改 VidAll_TV。
- 目标电视设备可由项目提供，用于 API 22、硬件解码、4K、HDR 和高规格音频的最终真机认证；无设备证据的能力保持“已构建待验证”或“暂缓”。
- 用户自行提供合法的 WebDAV 服务、凭据和具有再分发/测试授权的媒体素材；项目不保存或发布这些凭据与私人媒体。
- 首期采用 ARM64 电视为唯一承诺 ABI；x86_64 仅可用于非承诺性开发辅助，不能替代真机结论。
- Vulkan、RTSP、UDP、SRT、RTMP、杜比视界及音频直通不属于首期默认承诺，除非其单独验收记录满足本规格。
- 私有制品源、访问控制和发布凭据由项目受控环境提供；规格不预设具体供应商。发布凭据仅在受控发布环境中可用，且不进入源码、日志或发布物。
- 许可证结论需要在锁定的实际上游、编解码器和外部库组合确定后完成；构建开关本身不能替代许可证审计。

## 非目标

- 首期不交付桌面播放器界面、桌面命令行播放器或完整 GUI。
- 首期不承诺 x86_64 模拟器、所有电视型号、所有私有协议、所有 HDR/杜比格式或所有高规格音频直通。
- 首期不允许向 ArkTS 暴露可任意绕过安全、网络和文件访问策略的全量底层选项。
- 首期不改造、构建、提交、发布或以任何形式变更 VidAll_TV；其兼容性仅由本库的契约、矩阵和独立消费方验证界定。
- 首期不发布到未经批准的公共制品源，也不在规格中固定私有制品供应商或凭据机制。

## 用户场景与验收

### US1：当前视频窗口变化后向渲染端提交新尺寸（P1）

使用旧基线播放器的用户改变窗口尺寸时，当前 Vulkan 渲染端应收到新尺寸。不能仅更新播放器侧缓存，导致渲染端继续使用旧尺寸。该场景只解决 #83 已确认的通知缺失。

独立验收：播放视频并改变窗口尺寸，核对请求、提交返回值与渲染输出；主机测试先验证通知契约，消费端再验证实际画面。

1. 已绑定的当前代际收到有效尺寸后，窗口和渲染端均收到一致宽高。
2. 窗口调整或渲染端通知失败时，不能报告成功或留下被认可的错误尺寸。
3. 过时代际、空窗口、无效尺寸、未就绪或已释放会话应失败，不通知渲染端。
4. 连续改变尺寸及与 Detach 交错时，不能把通知发送到已脱离的窗口。

### US2：消费方取得可追溯的 CI 构建产物（P1）

维护者可以先本地构建和测试，再推送修复分支。最终交付须来自本项目 GitHub Actions，并能核验提交、run、哈希与依赖边界。

1. 同一 CI 提交按测试、完整构建、产物校验、上传顺序执行。
2. 测试、构建或校验失败不得上传为可交付 HAR；失败日志可单独保存。
3. 接入时可用 manifest 和 SHA-256 确认 CI 来源及未被替换的核心/运行库。

## 边界与非目标

- 原基线源码 `0ad5d6d3b52a39b342a50a413d4440f184107a22`；现用 HAR `826b667dcd315e75e71f89065c3aef4bd60ea73743916ee629469f93228c66a9`。
- FR-001：仅修改 Vulkan Resize 的通知缺失及直接必要的错误处理；其他原生方法、GL/SW 分支和全部 ArkTS 保持旧基线。
- FR-002：通知失败回滚窗口尺寸，回滚也失败时拒绝后续使用该 renderer，等待重新绑定。
- FR-003：保持现有初始化、公开 API、libmpv、共享库归属、最低 API 15 和目标 API 22；不引入整应用退出策略。
- FR-004：CI 必须完整编译 Player HAR，不得通过替换归档成员制作交付包；必须保存源码提交、run URL、实际工具链和库哈希。
- FR-005：只负责 mpv/Player；本轮不编译或修改 FFmpeg，不触发 `ohos_ijkplayer`。若发现该需求，提前说明边界，由用户安排。
- FR-006：#84 的广义旋转、GL/SW 暂停重绘、completed 通知不进入本轮；#83 消费端验收完成后再继续。
- FR-007：主机替身、CI 构建、模拟器与云/实体设备证据分别记录；不得把之前实验包结果用于当前 CI 包。

- SC-001：15 个尺寸回归场景通过，覆盖成功、错误回滚、重试、100 次尺寸切换和并发 Detach。

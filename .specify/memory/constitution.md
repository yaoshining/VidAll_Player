# VidAll HarmonyOS TV 工程宪章

## 核心原则

### 一、HarmonyOS 原生优先
必须优先使用 HarmonyOS 官方 API、ArkTS 和 ArkUI；禁止套用 Android、Java、Kotlin 或 Web 的架构与 API 假设，或伪造不存在的 API、组件、装饰器、权限和生命周期方法。使用不熟悉或版本敏感 API 前，必须查询对应 API 级别的官方文档。新增 API 必须确认 API 19 可用性；仅高版本可用的 API 必须进行版本判断并提供降级方案。禁止以 `any`、不安全类型断言或关闭类型检查掩盖 ArkTS 错误；公开接口、状态、回调和异步结果必须有明确类型。

### 二、TV 交互优先
所有页面和交互控件必须支持遥控器方向键、确认键与返回键，并有清晰、稳定、可预测的焦点顺序和明显视觉反馈。页面首次展示、弹窗开闭及返回后必须设置或恢复合理焦点。禁止焦点陷阱、焦点丢失、不可达控件、异常方向跳转，以及以触摸、滑动、长按或鼠标悬停作为核心操作的唯一方式。长列表必须验证连续导航、焦点跟随滚动和边界行为；返回键必须按临时界面、上级页面、退出应用的层级处理。界面必须适合电视观看距离，并避免遥控器长文本输入。

### 三、组件与状态架构
页面只负责组合、展示与交互；网络、存储、解析和播放器底层逻辑必须置于职责明确的服务、状态、数据模型或基础设施层。组件必须单一职责，可复用视觉或交互必须抽取；组件禁止直接修改外部所属状态。状态必须单向、可追踪，页面级、应用级和持久化状态必须区分，且同一事实不得有冲突来源。监听器、定时器、回调和系统资源必须在对应生命周期释放。禁止在 `build()` 或高频渲染路径进行网络、文件、复杂计算或不可控副作用；异步操作必须覆盖加载、成功、空数据、失败、取消和重试，共享状态只能经语义明确的方法修改。

### 四、媒体播放可靠性
播放器必须使用明确状态模型（至少覆盖 `idle`、`preparing`、`playing`、`paused`、`buffering`、`completed`、`error`、`released`），禁止以松散布尔值推断真实状态。初始化、切源、暂停、恢复、跳转、停止和释放必须可重复调用且可预测；切源前必须停止或释放旧资源，避免多实例、音频重叠和泄漏。页面退出、Ability 状态变化和后台进入必须有明确策略。进度、时长、缓冲和错误必须由统一状态源管理。网络媒体必须处理超时、断网、重连、地址失效和格式不支持；本地媒体必须处理文件不存在、权限拒绝、路径失效和读取失败。错误必须可理解、可恢复且不得导致无响应或崩溃。NAPI 或原生播放器必须声明所有权、线程边界与释放时机；禁止在 UI 主线程执行长时间解析、扫描或阻塞式原生调用。

### 五、权限、隐私与安全
权限必须最小化，并只在用户触发相关功能时申请和说明用途；拒绝后必须稳定降级或提供重新授权指引，禁止循环弹窗、强制退出或不可操作状态。禁止在源码、日志、配置或提交记录保存密码、密钥、令牌、证书口令和用户隐私数据；签名材料与环境凭据必须由安全配置或开发环境管理。日志必须脱敏，不得记录令牌、完整文件路径、个人数据或敏感媒体地址。网络请求必须校验输入、响应状态、数据结构与异常；URL、文件路径、Want 参数和跨模块输入均视为不可信。除非需求明确且已完成安全评审，禁止扩大 Ability 或 ExtensionAbility 导出范围。

### 六、性能与资源管理
首屏、切页、列表滚动和焦点移动不得被同步耗时任务阻塞。文件扫描、媒体解析、网络请求和大数据处理必须异步或后台执行；长列表必须使用懒加载、分页、缓存或增量更新。禁止在高频状态变化中重复创建大型对象、播放器实例或网络连接，媒体和图片必须按展示尺寸加载。系统资源、播放器、文件句柄、订阅、监听器和定时器必须有明确释放路径；状态更新范围必须限于依赖组件。优化必须基于测量，禁止以正确性、可读性或可维护性交换未经验证的收益；卡顿、内存增长和崩溃必须用日志、Profiler 或可复现测试定位，不得凭猜测修改。

### 七、错误处理与可观测性
网络、文件、权限、播放器、序列化和原生调用等外部操作必须显式处理异常。禁止空 `catch`、静默吞错和缺少上下文的日志。用户错误信息必须简明并尽量提供重试或恢复；开发日志必须包括模块、操作、状态和错误上下文且不得泄密。日志级别必须合理，调试日志不得默认污染发布版本。不可恢复错误必须安全终止当前操作，禁止遗留半完成或不一致状态。缺陷修复必须先明确复现条件和根因，禁止以延时、重复调用或吞异常掩盖问题。

### 八、测试与质量门禁
每项功能至少必须验证正常、空数据、加载、权限拒绝、网络异常、文件不可读、快速重复操作、页面离开后异步返回、遥控器焦点导航、返回键和播放器初始化释放；API 19 兼容策略必须明确并验证或记录不可验证原因。所有代码必须通过 ArkTS 编译与 Hvigor 构建，禁止新增编译错误、类型错误或未解释的高等级告警。核心业务逻辑必须有单元测试；导航、焦点、权限和媒体关键流程必须有集成测试或明确手工验收步骤。每项缺陷修复必须新增防回归测试或验收用例；禁止删断言、跳过测试或降低标准。发布前必须在目标 TV 真机或对应 TV 模拟器验证，禁止只依赖 Previewer。

### 九、代码可维护性
命名必须准确表达业务含义，禁止无意义缩写及模糊名称。函数必须短小、单一职责；复杂流程必须拆为可测试的语义步骤。禁止复制粘贴相同业务逻辑，必须抽取共享实现。注释只说明设计原因、限制和风险，不得逐行复述。公共接口、数据模型和关键状态转换必须有必要文档。禁止引入当前需求不需要的抽象、框架或依赖；新增依赖必须评估维护状态、许可证、包体积、HarmonyOS 兼容性和替代方案。变更必须范围清晰、易审查和回退；目录与命名约定优先，架构调整必须说明迁移理由。

### 十、需求与交付纪律
实现前必须明确用户场景、输入输出、异常路径和可验证验收标准；“优化体验”“提升性能”等表述必须转为可观察结果。技术方案必须说明 API 兼容性、状态模型、权限、失败恢复、焦点策略和资源释放。任务必须按可独立验证的垂直功能拆分，并包含完成定义、范围、验证方式和风险。需求、设计、任务和实现必须双向可追踪。面向项目的需求、设计、计划、任务、测试、验收、发布说明、变更日志、风险记录、代码审查和运维文档必须使用中文；第三方许可证、上游原始文档、协议字段、代码标识符及法律要求保留原文的内容可以同时保留原文并附中文说明。实现冲突时必须优先修改实现；禁止未经记录和批准绕过本宪章。

## 项目基线与适用范围
本项目为 HarmonyOS TV Stage 模型应用，使用 ArkTS、ArkUI、Hvigor 和 ohpm，主模块为 `entry`；核心场景为电视端媒体浏览、播放、文件访问和网络媒体访问。`targetSdkVersion` 必须为 HarmonyOS 6.0.2 / API 22，`compatibleSdkVersion` 必须为 HarmonyOS 5.0.3 / API 15。API 15 是安装兼容下限；所有新增 API 仍必须额外检查 API 19 可用性，并对 API 15–18 与 API 19–22 的差异实施运行时判断和降级。规范性语言中，“必须”不可违反，“禁止”无条件不允许，“应该”除非有明确书面理由否则必须遵守，“可以”为可选行为。

## 完成定义与质量门禁
功能只有在需求和验收标准满足、API 19–22 兼容策略明确、ArkTS 类型检查和 Hvigor 构建成功、正常异常边界路径验证、遥控器导航和焦点正确、权限及资源不可用可安全降级、播放器及系统资源释放、无新增敏感信息泄露、无未说明技术债务或临时绕过、中文项目文档和测试同步后才算完成。API 15–18 的安装与基础能力兼容策略也必须记录。

## 治理
本宪章高于普通需求、实现偏好和临时开发便利；所有 specification、plan、tasks、implementation、代码审查和发布验收必须执行一致性检查。修改宪章必须记录修改原因、影响范围、迁移方案、审批人和生效日期。删除安全、兼容性或质量约束为 MAJOR 变更；新增原则或实质扩大约束为 MINOR 变更；不改变语义的澄清为 PATCH 变更。无法遵守时，必须在实现前提交书面例外，说明原因、风险、替代措施、有效期限和审批人；禁止以进度紧张、实现方便或“暂时可用”作为无记录违反理由。
